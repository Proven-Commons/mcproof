A domain a model cannot talk its way out of.

mcproof gives AI models a working domain where results are proofs and checkers, judged by programs that give the same answer every run. A model may propose. It may never approve its own work. The goal is the one Foundation-0 set: put models to work on open science and mathematics, with every step on the record and checkable.

This page is written as a proof. Each claim below is a numbered record with a kind (axiom, lemma, obligation), a certainty tier, the claims it uses, and its evidence. Nothing here is labelled by hand: two checkers that share no code recompute every tier from one data file, once in CI before this page could publish, and once in your browser as you read. If the graph breaks, the seal turns red.

    00//Axioms

    the trust base, stated not proved

    Four rules everything else stands on.

    An axiom here is a design commitment, not a discovered fact. Each one is listed so a reader can disagree with it by name. The checkers treat axioms as given, and the section What you must trust repeats them without decoration.

    Axiom A1Known

    Model weights never hold authority

    A trained adapter may carry habits. It may never carry the right to approve a spec, admit a proof, or overrule a checker. Approval stays with named people; enforcement stays with programs anyone can rerun.

    Evidence
    • Blueprint, three-tier placement
    Axiom A2Known

    When in doubt, refuse

    Every gate in the stack fails closed. A stale manifest, a forged certificate, or a contested rule stops the load instead of guessing. A refusal is a valid result; a silent pass is not.

    Evidence
    • Blueprint, hard vetoes
    Axiom A3Known

    Exact arithmetic in exact checkers

    A checker for exact mathematics uses integers and fractions only. No floating point value may decide whether an exact claim passes, because rounding can turn a false claim true.

    Evidence
    • finite-state-proofs verify.py, the reference checker
    Axiom A4Known

    Say what is not proved

    Every formal write-up states what it does not prove and what a reader must trust without proof. A result with no stated boundary is treated as a claim with no stated scope, and does not pass the bar.

    Evidence
    • The verified bar, Proven-Commons/mission

    01//Definitions

    Words, pinned down.

    Definition D1Known

    A zone is a span of text with one set of rules

    A Multi-Domain Editing (MDE) zone marks a span, such as a proof block or a JSON record, and names which rules govern it. Precedence runs formal proof, then condensed JSON, then interface code, then ordinary code, then prose.

    Evidence
    • zone-manifest.v0.1.json
    Definition D2Known

    Five words for how sure we are

    OPEN means nobody has discharged it yet. CONJECTURE means stated, not proved. KNOWN means established prior work or a stated axiom. VERIFIED means a named checker was run and passed. PROVEN means a proof checker accepted a complete proof with no escape hatches.

    Evidence
    • Foundation-0 REPO-STANDARD.md
    Definition D3Known

    A deterministic oracle gives the same answer every run

    An oracle here is a program, never a language model, whose verdict on the same input is byte-identical on every run: a Lean build, an auditor script, a schema check. If a verdict can drift between runs, it cannot gate anything.

    Uses A3

    Evidence
    • Blueprint, oracle catalog

    02//Lemmas: the verified baseline

    source: blueprint issue, commits pinned

    What already stands, layer by layer.

    Five pieces exist today and have been run: the source specs with their oracles, and layers 2 to 5 of the stack that compiles, loads, routes, and audits model adapters. Each lemma names its commit. VERIFIED here means the blueprint records a checker run against that artifact; it does not mean the end-to-end claim holds. That claim is T0, and it is still a conjecture.

    Lemma L1Verified

    The source specs and oracles exist and are public

    About 32.7k tokens of formal-verification source specs sit in public repositories, with working oracles: the soko auditors, bar/check.py, and f0/scripts/gate.py. The formal-claims-audit ledger holds zero verdicts so far, and its reviewer list is empty.

    Uses D3

    Evidence
    • soko auditors
    • f0 claim gate
    • 18-package Lean v4.35.0 anthology
    Lemma L2Verified

    Layer 5 classifies zones and audits generated code

    The mde tool carries a canonical zone manifest (sha256 4e00656c...) and a native guard that rejects bare asserts, silent exception swallows, and duplicate JSON keys in generated verifiers.

    Uses D1, D3

    Evidence
    • siliconcordat/mde at 52ce0178
    Lemma L3Verified

    Layer 4 routes proof spans to the proof adapter only

    The exo router sends a formal_proof span to the formal-verification adapter at weight 1.0 and to the prose and style packs at 0.0. Unit tests cover all seven cross-domain interference rules.

    Uses D1

    Evidence
    • siliconcordat/exo at 9d52aa1f
    Lemma L4Verified

    Layer 3 loads adapters through four fail-closed stages

    The warp-modeld daemon checks binding, an integer certificate, a shadow load with verifier-owned canaries, and a constant-time kill switch, in that order. It was live-verified against llama-server with 54 of 54 tests passing.

    Uses A2, D3

    Evidence

    Lemma L5Verified

    Layer 2 compiles adapters you can rebuild byte for byte

    The weft compiler solves its edit in CPU float64, packs it into a checked container, and certifies the packed result with integer arithmetic. Experiments E1 to E7 cover composition, tamper rejection, packing, and a live server load. The composition runs so far are synthetic.

    Uses A2, A3

    Evidence
    • siliconcordat/weft at 3d66f07e, RESULTS.md

    03//Theorems

    One conjecture worth testing. One theorem about this page.

    Theorem T0Conjecture

    A model can work inside a formal domain it cannot talk its way out of

    A model fitted with the formal-verification adapter, mounted through layers 2 to 5, produces proofs and checkers that pass deterministic oracles at rates the bare model does not reach, while every authority stays outside the weights. This is the claim mcproof exists to test. It is not proved, and this site will not call it proved until O1 to O4 are discharged.

    Uses L1, L2, L3, L4, L5, O1, O2, O3, O4

    Evidence
    • Blueprint issue, siliconcordat/mde#4

    04//Obligations

    open until discharged, in the open

    The proof obligations, still open.

    In a proof assistant, an unfinished proof lists its remaining goals. Same here: five obligations stand between the verified baseline and Theorem T0. Each states what would discharge it. The checkers cap T0 at CONJECTURE while any of them is open, so this page cannot quietly upgrade itself.

    Obligation O1Open

    Freeze a 240-prompt test set with a private holdout

    Assemble 240 prompts in four families (Lean proofs, exact checkers, claim-tier traps, mixed-zone documents), split 96 compile, 48 validation, 96 untouched private holdout, and pin every record by SHA-256. Discharge: the frozen manifest and its sums file exist and recompute.

    Uses L1

    Obligation O2Open

    Compile a real 1.7B to 4B adapter and score it live

    Build the formal-verification adapter for a real open checkpoint and score it against the Lean compiler and the soko, bar, and f0 oracles. Discharge: scored runs on the frozen set, with the bare model and the full-spec prompt as matched arms.

    Uses O1, L5

    Obligation O3Open

    Meet the pre-registered pass and kill criteria

    Pass means at least 50 percent fewer oracle failures than the bare model on the private holdout, at least 80 percent of the full-spec ceiling, all safety canaries green, and zero corrupted proof blocks. Discharge: the scored table, published either way. A miss on deep proof search is published as a negative result, not re-gated.

    Uses O2, L4

    Obligation O4Open

    Compose with prose and style packs without interference

    Run the proof adapter beside a prose pack and the Eido style system under gates T-C1 to T-C5: solo gains kept, zones isolated, base ability retained, order-invariant composition, and a serving budget. Discharge: all five gates scored on a real checkpoint.

    Uses O3, L3

    Obligation O5Open

    Seat the human bar

    Name spec reviewers in bar/reviewers.toml and record the first verdicts in formal-claims-audit. Until then the human tier of the system is specified but unstaffed, and no library counts as admitted. Discharge: a non-empty reviewer list and at least one recorded verdict.

    Uses A1

    05//Hazard guards

    counterexamples, each with its guard

    Seven ways the domains could corrupt each other.

    Put a proof domain beside a prose domain and a style domain and the seams are where things break: a style rule edits a proof, a summary trims a disclaimer. Each known seam is recorded as a hazard with the guard that closes it. Precedence when rules collide: human authority, then repository policy, then the specialist pack inside its own zone, then the base prose pack.

    Hazard guard H1Known

    A style rule against negative clauses could strip the honesty sections

    Guard: inside a formal_proof zone the prose pack weight is 0.0 and negative disclaimers are explicitly allowed, so What is not proved survives every style pass.

    Uses A4, D1

    Hazard guard H2Known

    Readability rules could rewrite axioms and commit hashes

    Guard: protect_axioms and protect_sha_digests pin exact identifiers. A 40-character verdict hash is never shortened to please a style rule.

    Uses D1

    Hazard guard H3Known

    Two vocabularies for certainty could blur into each other

    Guard: claim-tier words are locked per repository by policy, outside the weights. Tested and deployed never silently become VERIFIED or PROVEN.

    Uses D2

    Hazard guard H4Known

    Prose grammar rules could mangle terse machine records

    Guard: a condensed_json zone with no formal claims zeroes the prose pack, so grammar rules never reach inside a data record.

    Uses D1

    Hazard guard H5Known

    Two delivery styles could each claim the same page

    Guard: a contested delivery choice fails closed with ContestedPreferenceError until a human-written precedence override names the winner.

    Uses A1, A2

    Hazard guard H6Known

    A floating-point picture could pose as an exact result

    Guard: research pages forbid floats inside exact verifiers and require every illustrative figure to carry an illustrative tag and a link to its certificate.

    Uses A3

    Hazard guard H7Known

    Automatic shortening could cut the hedges off a claim

    Guard: condensing refuses any block marked data-eido-skip. On this page the condense switch shortens plain prose and visibly refuses every proof block. Try it in the header.

    Uses A4, D1

    06//Boundary

    What is not proved.

    • Theorem T0. No end-to-end run on a real checkpoint exists yet; composition evidence so far is synthetic.
    • That a compiled adapter can carry deep proof search, as opposed to surface habits such as exact arithmetic and honest tiers. The blueprint records this as the likely failure line in advance.
    • Any admission to the Proven Commons bar. The reviewer list is empty and the verdict ledger holds zero verdicts (Obligation O5).
    • The lemmas rest on runs recorded in the blueprint issue. They were not rerun for this page; the commits are pinned so anyone can rerun them.
    • This page proves a property of its own claim graph (T1), nothing about any model.

    What you must trust.

    • Axioms A1 to A4. They are commitments, and the system is only as good as they are.
    • The oracles themselves: the Lean toolchain, and the auditor scripts named in L1. A bug in an oracle is a bug in every verdict it gates.
    • For this page: your browser's SHA-256, and that the two checkers in the repository are the ones CI ran. Both are short and readable.
    • GitHub, to serve the files the repository holds. The certificate lets you detect any difference, but not prevent it.

    07//Verify

    no proof, no publish

    Do not take this page's word for it.

    Clone the repository and run the same gates CI runs. The Python checker runs three ways, including with optimisations and warnings as errors. The JavaScript checker runs under Node and must agree with the Python certificate claim by claim. Twelve planted corruptions of the graph must all be rejected. The page is then built twice and the two builds must be byte-identical. Only if all of that passes does the publish job run.

    git clone https://github.com/Proven-Commons/mcproof
cd mcproof
python3 -I -B   tools/verify.py --write-certificate
python3 -I -O -B tools/verify.py
python3 -I -B -W error tools/verify.py
python3 -I -B tools/run_mutations.py     # 12 planted bugs, all must be rejected
node --test "test/*.test.mjs"            # JS checker vs the Python certificate
python3 -I -B tools/build.py --verify    # deterministic prerender

    To add or change a claim, edit docs/data/claims.json, keep the tier rules in RULES.md, and rerun the gates. The page text, the figure, the stats, and the seal all rebuild from that one file.
